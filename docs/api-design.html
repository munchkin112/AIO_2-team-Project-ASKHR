1. 개요

AskHR 백엔드는 FastAPI로 구현된 단일 서비스이며, 인증·데이터는 Supabase, 캐시·사용량 로그는 Redis, 답변 생성은 Google Gemini를 사용한다. 클라이언트(웹 프런트엔드)는 이 문서의 엔드포인트만 호출하며 Supabase·Redis·Gemini에 직접 접근하지 않는다.

구성 요소역할비고
FastAPIREST · SSE API 서버제목 AskHR, 버전 0.1.0
Supabase Auth회원가입 · 로그인 · JWT 발급/검증이메일 + 비밀번호 방식
Supabase Postgresconversations, messages, profiles 테이블RLS(행 수준 보안)로 소유자 검사
Redis세션 캐시(5분), 메시지 목록 캐시(5분), 사용량 로그(대화당 최근 50건)사용량 로그는 운영 기록이며 서비스 데이터가 아님
Google Gemini답변 생성 (gemini-3.5-flash-lite, 스트리밍)시스템 프롬프트에 규정 MD 본문을 삽입 (키워드 기반 선택)

1.1 인증 방식

  • 인증 방식은 HTTP Bearer이다. POST /auth/login 또는 POST /auth/signup 응답의 access_token을 이후 모든 요청의 헤더에 담는다.
  • 헤더 형식: Authorization: Bearer <access_token>
  • 토큰은 Supabase에 검증을 위임하며, 검증 결과는 토큰 해시를 키로 Redis에 300초 캐시된다. 만료·위조 토큰은 401 유효하지 않은 토큰입니다로 응답한다.
  • 보호된 엔드포인트는 아래 요약표에서 🔒로 표시한다. /auth/*, /health만 인증 없이 호출할 수 있다.
  • 대화 소유권은 서버가 직접 비교하지 않고 RLS가 적용된 조회 결과로 판단한다. 존재하지 않는 대화와 타인의 대화는 구분 없이 동일하게 404로 응답한다 (대화 존재 여부 노출 방지).

1.2 공통 규칙

각 이벤트는 data: <JSON> 한 줄과 빈 줄로 구성된다. 이벤트 종류는 JSON의 키로 구분한다.

이벤트페이로드발생 시점 · 처리
text{"text": "<조각>"}모델이 생성한 텍스트 조각. 도착한 순서대로 이어 붙여 표시한다 (SCR-004-E04 스트리밍 상태). 조각 안의 줄바꿈은 JSON으로 이스케이프되어 있으므로 파싱 후 그대로 붙인다
done{"done": true, "message_id": "<uuid>"}정상 종료. 답변이 messages에 저장되고 사용량 로그가 기록된 뒤 마지막으로 1회 전송. 클라이언트는 이 이벤트 후 GET /conversations/{id}/messages와 GET /me/conversations를 재조회해 저장본과 갱신된 제목을 반영한다
error{"error": "<메시지>"}스트림 시작 후 발생한 실패. 이미 200으로 응답이 열려 있어 HTTP 상태를 바꿀 수 없으므로 이벤트로 통지한다. 이 이벤트 뒤에는 done이 오지 않으며 답변은 저장되지 않는다 (사용자 질문은 이미 저장됨). 대표 원인: Gemini 일일 한도 초과(429), 모델 오류, 빈 응답

응답 예시 (스트림)

data: {"text": "복리후생 제도로는 복지포인트, 건강검진, "}

data: {"text": "자기계발비, 도서구입비, 식대 및 야근 식대, "}

data: {"text": "경조휴가 및 경조사비, 심리상담 지원이 있습니다.\n\n[복리후생규정 > 복지포인트] [복리후생규정 > 건강검진]"}

data: {"done": true, "message_id": "5e1f2a3b-3333-4b2c-8f9a-2a3b4c5d6e7f"}
// 한도 초과 등 실패 시
data: {"error": "ClientError: 429 RESOURCE_EXHAUSTED ..."}

서버 처리 순서

  1. 토큰 검증 후 대화 소유 여부 확인 (실패 시 401 / 404).
  2. 대화 제목 조회. 이력 구성: 마지막 system 메시지 이후만 남기고, user/assistant만 골라 최근 20개로 제한.
  3. 질문 키워드로 규정 MD 파일 선택 (부록 6.1). 새 키워드가 없고 후속 질문 표현이면 직전 사용자 질문의 주제를 잇는다. 파일 읽기 실패 시 503.
  4. 사용자 메시지를 먼저 저장 → 첫 사용자 메시지라면 대화 제목을 본문 앞 50자로 자동 갱신 (SCR-002-E06 안내 문구의 근거). 메시지 캐시 무효화.
  5. 시스템 프롬프트 + 이력 + 질문으로 Gemini 스트리밍 호출. 조각마다 text 이벤트 전송.
  6. 정상 종료 시 전체 답변을 assistant 메시지로 1회 저장, Redis usage_log:{conversation_id}에 지연시간·토큰 기록(최근 50건 유지), done 이벤트 전송.

시퀀스 다이어그램

실선: 요청 / 점선(보라): 응답·스트림. Supabase 호출은 RLS가 적용된 클라이언트(소유 확인)와 서버 전용 클라이언트(저장·제목 갱신)를 구분해 사용한다.

6.3 대화 제목 자동 생성

  • 대화 생성 시 제목은 클라이언트가 보낸 값(“새 대화”)이다.
  • 첫 번째 사용자 메시지가 저장될 때 본문의 연속 공백을 하나로 줄이고 앞 50자를 제목으로 갱신한다. 비어 있으면 “새 대화”.
  • 두 번째 이후 메시지는 제목을 바꾸지 않는다. 클라이언트는 done 이벤트 후 GET /me/conversations로 제목을 다시 읽는다.

6.4 알려진 제한 · 후속 과제

  • GET /conversations/{id}/messages는 최대 20건 고정 — 페이지 파라미터 노출 필요.
  • ChatRequest.tone / length는 수신만 하고 프롬프트에 반영하지 않음.
  • 서버 측 요청 빈도 제한(rate limit) 없음. Gemini 한도 초과는 SSE error 이벤트로만 드러난다.
  • 분석 API는 로그인 사용자 전체에 열려 있음 — 운영 전환 시 관리자 권한 분리 필요.
  • /health는 프로세스 생존만 확인하며 의존 서비스 상태를 포함하지 않는다.
