# ASKHR 규정 문서 활용 가이드

## 1. 목적

이 가이드는 프로젝트용 Markdown 규정 8개를 ASKHR 챗봇의 답변 근거로 사용하는 방법을 설명한다.

핵심 원칙은 다음과 같다.

1. LLM이 회사 규정을 임의로 만들어 답하지 않게 한다.
2. 먼저 관련 규정 조항을 검색한 뒤, 검색된 내용만 LLM에 전달한다.
3. 답변에 문서명과 조항 ID를 표시해 사용자가 근거를 확인할 수 있게 한다.
4. 개인정보나 개인별 판단이 필요한 질문은 담당 부서 안내로 전환한다.

## 2. 문서 구성

| 파일 | 문서 코드 | 주요 내용 |
|---|---|---|
| `휴가_근태규정.md` | `POL-LEAVE` | 연차, 반차, 병가, 출산휴가, 육아휴직, 근무시간 |
| `복리후생규정.md` | `POL-WELFARE` | 복지포인트, 건강검진, 교육비, 도서비, 식대, 경조사 |
| `급여규정.md` | `POL-PAY` | 급여일, 명세서, 급여계좌, 추가근무, 연말정산 |
| `출장_경비처리규정.md` | `POL-EXPENSE` | 출장 신청, 교통·숙박·식비, 법인카드, 정산 |
| `정보보안_IT이용규정.md` | `POL-IT` | 계정, 비밀번호, Wi-Fi, VPN, 자료보호, 보안 신고 |
| `시설이용규정.md` | `POL-FACILITY` | 사원증, 회의실, 방문객, 좌석, 주차 |
| `인사규정.md` | `POL-HR` | 수습기간, 조직도, 증명서, 정보 변경, 이동, 퇴직 |
| `신입사원_온보딩가이드.md` | `GUIDE-ONBOARDING` | 입사 준비, 첫날·첫 주·첫 달 체크리스트 |

각 `##` 제목은 하나의 검색 단위다. 예를 들어 `## LEAVE-003 병가`부터 다음 `##` 전까지를 하나의 FAQ 조각(chunk)으로 저장한다.

## 3. 구현 방법 비교

| 방식 | 장점 | 단점 | 2일 MVP 판단 |
|---|---|---|---|
| Markdown 전체를 프롬프트에 넣기 | 구현이 가장 빠름 | 토큰 낭비, 문서 증가 시 정확도 저하 | 시연용 임시 방식 |
| 키워드 검색 | 단순하고 결과를 설명하기 쉬움 | 표현이 다른 질문에 약함 | 기본 기능으로 적합 |
| 임베딩 유사도 검색 | 자연어 표현이 달라도 찾기 좋음 | 설정과 디버깅이 추가로 필요 | 가능하면 적용 |
| 키워드+임베딩 하이브리드 | 정확도와 유연성의 균형이 좋음 | 점수 결합 로직 필요 | **권장** |

### 권장 범위

- 1순위: 조항 단위 데이터 적재, 키워드 검색, 출처 표시
- 2순위: Supabase `pgvector`를 이용한 임베딩 유사도 검색 추가
- 제외: 복잡한 문서 자동 수집, 재순위화 모델, 에이전트형 다단계 검색

## 4. 권장 전체 흐름

```text
[최초 1회: 데이터 준비]
Markdown 8개 읽기
  → ## 조항 단위로 분리
  → 문서명·조항 ID·제목·본문·키워드 추출
  → 본문 임베딩 생성(선택)
  → Supabase faq_rules 테이블에 저장

[사용자 질문마다 실행]
사용자 질문 입력
  → FastAPI /api/chat 호출
  → Redis에서 최근 대화 조회
  → 질문에서 핵심 단어 추출
  → Supabase에서 키워드/제목 검색
  → 임베딩 유사도 검색(선택)
  → 점수가 높은 조항 3개 선택
  → 질문 + 최근 대화 + 검색 조항을 LLM에 전달
  → 근거에만 기반한 답변 생성
  → 답변과 출처를 Redis에 저장
  → Frontend에 답변 + 출처 반환
```

## 5. Supabase 데이터 구조

테이블명은 `faq_rules`를 권장한다.

| 컬럼 | 타입 예시 | 설명 |
|---|---|---|
| `id` | `bigint` | DB 내부 ID |
| `rule_id` | `text unique` | `LEAVE-003` 같은 조항 ID |
| `document_code` | `text` | `POL-LEAVE` 같은 문서 코드 |
| `document_name` | `text` | 출처에 표시할 파일명 |
| `category` | `text` | 휴가·근태, 복지, IT 등 |
| `title` | `text` | 조항 제목 |
| `content` | `text` | 조항 본문 전체 |
| `keywords` | `text[]` | 문서에 적힌 검색 키워드 |
| `version` | `text` | `2026.09-v1` |
| `embedding` | `vector` | 임베딩 벡터, 선택 사항 |
| `is_active` | `boolean` | 현재 사용 여부 |
| `updated_at` | `timestamptz` | 변경 시각 |

### 저장 예시

```json
{
  "rule_id": "LEAVE-003",
  "document_code": "POL-LEAVE",
  "document_name": "휴가_근태규정.md",
  "category": "휴가·근태",
  "title": "병가",
  "content": "질병이나 부상으로 근무하기 어려운 경우 연간 최대 10일의 유급 병가를 사용할 수 있다...",
  "keywords": ["아파서 쉬기", "병가 며칠", "진단서", "병원", "병가 신청"],
  "version": "2026.09-v1",
  "is_active": true
}
```

## 6. 검색 로직

### MVP용 단순 검색

1. 질문과 조항의 `title`, `keywords`, `content`를 비교한다.
2. 제목 일치에는 높은 점수, 키워드 일치에는 중간 점수, 본문 일치에는 낮은 점수를 준다.
3. 상위 3개 조항을 LLM에 전달한다.
4. 최고 점수가 너무 낮으면 억지로 답하지 않고 담당 부서 문의를 안내한다.

점수 예시는 다음과 같다.

```text
제목에 질문 단어 포함       +5점
keywords 항목과 일치       +3점
본문에 질문 단어 포함       +1점
대화의 직전 질문과 같은 범주 +1점
```

### 권장 하이브리드 검색

```text
최종 점수 = 키워드 점수 40% + 임베딩 유사도 60%
```

FAQ가 50개 안팎이면 복잡한 검색 엔진은 필요 없다. 정확한 비율보다 테스트 질문에서 올바른 조항이 상위 3개 안에 들어오는지가 중요하다.

## 7. LLM 프롬프트 구성

### 시스템 지침 예시

```text
너는 신입사원을 돕는 사내 FAQ 챗봇 ASKHR이다.
반드시 제공된 [검색된 규정]만 근거로 답한다.
규정에 없는 금액, 기간, 절차를 추측하거나 만들어내지 않는다.
답은 먼저 핵심 내용을 말하고, 필요한 절차와 준비 서류를 쉽게 설명한다.
근거가 부족하면 모른다고 말하고 적절한 담당 부서를 안내한다.
개인정보, 급여 상세, 징계, 평가 등 개인별 판단은 담당 부서에 문의하도록 안내한다.
답변 마지막에 사용한 조항 ID와 문서명을 출처로 표시한다.
```

### 사용자 질문에 함께 전달할 내용

```text
[최근 대화]
사용자: 다음 달에 결혼해요.
도우미: 본인 결혼에 관한 지원을 확인해 드릴게요.

[검색된 규정]
- WELFARE-006 경조휴가 및 경조사비
  본인 결혼: 유급휴가 5일, 경조사비 50만 원...

[현재 질문]
무슨 서류를 내야 하나요?
```

이렇게 최근 대화를 함께 보내야 LLM이 `무슨 서류`가 본인 결혼 서류를 뜻한다는 것을 이해할 수 있다.

## 8. FastAPI API 예시

### `POST /api/chat`

요청:

```json
{
  "session_id": "session-1234",
  "message": "다음 달에 결혼하는데 회사 지원이 있나요?",
  "answer_mode": "friendly"
}
```

응답:

```json
{
  "answer": "본인 결혼 시 유급휴가 5일과 경조사비 50만 원을 지원합니다...",
  "sources": [
    {
      "rule_id": "WELFARE-006",
      "document_name": "복리후생규정.md",
      "title": "경조휴가 및 경조사비"
    }
  ],
  "session_id": "session-1234",
  "needs_human_help": false
}
```

### 함께 두면 좋은 API

| API | 용도 | 우선순위 |
|---|---|---|
| `POST /api/chat` | 질문, 검색, LLM 답변 | 필수 |
| `POST /api/sessions` | 새 대화 생성 | 필수 |
| `DELETE /api/sessions/{id}` | 현재 대화 초기화 | 필수 |
| `GET /api/categories` | 카테고리와 추천 질문 | 권장 |
| `POST /api/feedback` | 답변 만족도 | 선택 |

## 9. Redis 사용 범위

Redis에는 영구 규정이 아니라 짧게 유지할 대화 상태를 저장한다.

- 키 예시: `chat:session-1234`
- 값: 최근 사용자·챗봇 메시지 6~10개
- 만료시간: 마지막 대화 후 24시간
- 추가 캐시: 자주 묻는 질문의 검색 결과를 10~30분 저장

규정 원본은 Supabase에 저장한다. Redis만 사용하면 서버 재시작이나 만료 시 규정 데이터가 사라질 수 있다.

## 10. 답변 안전장치

- 검색 결과가 없으면: `확인할 수 있는 규정이 없습니다. 인사팀에 문의해 주세요.`
- 서로 다른 규정이 충돌하면: 최신 `version`의 활성 조항을 우선하고 담당 부서 확인을 안내한다.
- 개인정보가 포함되면: 저장하거나 LLM에 전달하기 전에 마스킹하고 사용자에게 입력 금지를 안내한다.
- 보안 사고 질문이면: 일반 설명보다 `즉시 정보보안팀 신고`를 먼저 표시한다.
- LLM 응답이 실패하면: 검색된 원문을 요약하지 않고 그대로 보여 주거나 재시도 버튼을 제공한다.
- 모든 답변에는 최소 한 개의 출처를 표시한다. 출처가 없으면 규정 답변으로 취급하지 않는다.

## 11. 데이터 적재 시 주의사항

1. 파일 하나를 통째로 한 레코드로 저장하지 않는다.
2. 문장을 임의 글자 수로 자르지 말고 `## 조항`을 기준으로 나눈다.
3. 조항 ID는 바꾸지 않는다. 제목이 수정돼도 기존 링크와 로그를 추적할 수 있다.
4. 같은 사실을 여러 문서에 중복 저장하지 않는다. 필요한 경우 다른 조항을 참조한다.
5. 문서를 수정하면 `version`을 올리고 임베딩을 다시 생성한다.
6. 원본 Markdown은 Git으로 관리하고 Supabase 데이터는 다시 생성할 수 있게 한다.

## 12. 테스트 질문 세트

다음 질문에서 기대한 조항이 검색되는지 확인한다.

| 테스트 질문 | 기대 조항 |
|---|---|
| 입사하면 연차가 며칠 생기나요? | `LEAVE-001` |
| 오후에 병원에 가려면 어떻게 하나요? | `LEAVE-002` 또는 `LEAVE-004` |
| 아파서 사흘 쉬면 진단서가 필요한가요? | `LEAVE-003` |
| 다음 달에 제가 결혼하는데 지원이 있나요? | `WELFARE-006` |
| 할머니 장례가 생겼어요. 며칠 쉴 수 있나요? | `WELFARE-006` |
| 온라인 강의도 회사에서 지원하나요? | `WELFARE-003` |
| 월급은 언제 들어오나요? | `PAY-001` |
| 출장 영수증을 잃어버렸어요. | `EXPENSE-007` |
| 집에서 사내 시스템에 접속하고 싶어요. | `IT-004` |
| 수상한 메일 링크를 눌렀어요. | `IT-007` |
| 사원증을 잃어버렸어요. | `FACILITY-002` |
| 재직증명서는 어디서 발급하나요? | `HR-003` |
| 첫 출근 때 무엇을 가져가야 하나요? | `ONBOARD-001` |

추가로 다음 항목을 확인한다.

- 후속 질문: `그럼 무슨 서류가 필요해요?`
- 범위 밖 질문: `올해 회사 매출은 얼마예요?`
- 개인정보 포함 질문: `제 계좌번호는 123-...인데 월급이 왜 안 왔죠?`
- 모호한 질문: `휴가는 어떻게 돼요?`
- 장애 상황: Supabase, Redis 또는 LLM API가 응답하지 않을 때 안내가 표시되는가?

## 13. 2일 구현 순서

### 월요일

1. 오전: Markdown 파서와 Supabase 테이블 구성
2. 오전~오후: 조항 적재 및 키워드 검색 API 구현
3. 오후: 채팅 화면, 새 대화, 추천 질문 구현
4. 오후: `/api/chat` 응답 형식을 기준으로 FE/BE 연동

### 화요일

1. 오전: Redis 최근 대화와 LLM 답변 생성 연결
2. 오전: 출처 표시와 오류 처리
3. 오후: 테스트 질문 13개 검증 및 프롬프트 수정
4. 오후: UI 정리, 시연 시나리오와 발표 준비

임베딩 검색은 키워드 검색과 기본 대화가 먼저 완성된 뒤 추가한다. 시간이 부족하면 키워드 검색만으로도 MVP 시연이 가능하다.

## 14. 추천 시연 시나리오

```text
사용자: 다음 달에 결혼하는데 회사에서 지원해주는 게 있나요?
ASKHR: 본인 결혼 시 유급휴가 5일과 경조사비 50만 원을 지원합니다...
출처: 복리후생규정.md · WELFARE-006

사용자: 신청할 때 뭘 내야 해요?
ASKHR: 청첩장 또는 혼인관계증명서가 필요합니다...
출처: 복리후생규정.md · WELFARE-006
```

첫 질문에서는 자연어 검색과 정확한 규정 안내를, 두 번째 질문에서는 Redis에 저장된 대화 맥락 유지 기능을 보여 줄 수 있다.
