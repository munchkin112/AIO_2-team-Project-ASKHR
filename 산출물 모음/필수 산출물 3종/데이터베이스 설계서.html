1. 개요

1.1 목적

AskHR AI 챗봇 서비스가 사용자·대화·메시지를 영구 보관하고, 운영 지표(응답 지연 · 토큰 사용량)를 가볍게 기록하기 위한 데이터 구조를 정의한다. 기획·개발·운영 담당자가 같은 기준으로 테이블, 관계, 접근 권한, 삭제 정책을 이해하는 것을 목적으로 한다.

1.2 저장소 구성

저장소보관 대상성격장애 시 동작
Supabase Auth (auth.users)계정 · 이메일 · 비밀번호 해시 · JWTSupabase 관리형. 앱은 직접 읽고 쓰지 않는다로그인 · 토큰 검증 불가

1.3 설계 원칙

  • 계정과 프로필 분리 — 이메일·비밀번호는 Supabase Auth가 관리하고, 앱 테이블은 profiles만 갖는다. 가입 시 트리거가 프로필을 자동 생성한다.
  • 소유권은 DB가 판단 — 앱 코드가 user_id를 비교하지 않고 RLS(행 수준 보안) 정책이 “내 행”만 보이게 한다. 없는 행과 남의 행이 똑같이 0건으로 보여 존재 여부가 새지 않는다.
  • 계층형 삭제 — 사용자 → 대화 → 메시지 순으로 ON DELETE CASCADE. 고아 행을 남기지 않는다.
  • 운영 기록은 관계형 테이블에 넣지 않는다 — 응답 지연·토큰은 Redis 리스트에 대화당 최근 50건만 남긴다. 서비스 데이터가 아니므로 유실을 허용한다.
  • 시각은 모두 TIMESTAMPTZ — UTC로 저장하고 화면에서 KST로 변환한다.

2. ERD

2.1 논리 ERD

한 사용자는 여러 대화를 진행하고, 한 대화는 여러 메시지를 포함한다. 대화는 반드시 사용자에게, 메시지는 반드시 대화에 속한다 (선택적 관계 없음).

구현 참고

  • 코드 확인 생성: POST /me/conversations가 {user_id, title}를 INSERT (RLS “insert own conversations”가 user_id = auth.uid()를 강제).
  • 코드 확인 제목 자동 갱신: 대화의 첫 번째 user 메시지가 저장될 때 본문의 연속 공백을 하나로 줄여 앞 50자를 title로 UPDATE. 비면 '새 대화'. 이 갱신은 서비스 롤로 수행된다.
  • 코드 확인 제목이 NULL/빈 값이면 채팅·대시보드는 '대화 미지정'으로 표시한다.
  • 후속 과제 updated_at을 갱신하는 코드나 트리거가 없다. 현재는 created_at과 같은 값으로 남는다 (10장).
messages대화 메시지
특정 대화 안에서 주고받은 개별 메시지를 저장한다. 사용자 질문, AI 답변, 그리고 맥락 초기화 지점을 나타내는 시스템 메시지가 한 테이블에 시간순으로 쌓인다.
컬럼명데이터 타입키Null기본값제약조건 / 설명
idUUIDPKNOT NULLgen_random_uuid()메시지 고유 식별자. SSE done 이벤트의 message_id
conversation_idUUIDFKNOT NULL-소속 대화. conversations.id 참조, ON DELETE CASCADE
roleVARCHAR(20)-NOT NULL-작성 주체. 'user' 사용자 · 'assistant' AI · 'system' 맥락 구분선
contentTEXT-NOT NULL-메시지 본문. AI 답변은 마지막 줄에 [규정명 > 항목명] 근거 표기를 포함
created_atTIMESTAMPTZ-NOT NULLCURRENT_TIMESTAMP생성 일시. 조회 정렬 기준(오름차순)

구현 참고

  • 코드 확인 저장 순서: 질문 수신 → user 행 INSERT → (첫 메시지면 제목 갱신) → 모델 스트리밍 → 완료 시 assistant 행 1건 INSERT. 스트림이 실패하면 assistant 행은 남지 않고 user 행만 남는다.
  • 코드 확인 role 값은 앱의 Pydantic Literal["user","assistant","system"]이 강제한다. DB의 CHECK 제약은 SQL에서 확인되지 않았다 (10장).
  • 코드 확인 모델에 보내는 이력은 마지막 system 행 이후의 user/assistant 최근 20건이다. system 행은 “여기서부터 새 맥락”을 뜻하는 경계 역할만 하며 모델에 전달되지 않는다.
  • 코드 확인 이 테이블의 읽기·쓰기는 모두 서비스 롤 클라이언트로 수행되어 RLS를 우회한다. 접근 통제는 상위의 대화 소유 확인(require_own_conversation)이 담당한다 (7장).

관계자식 컬럼 → 부모 컬럼카디널리티ON DELETE효과근거

5. 트리거 · 함수

코드 확인 docs/db/01_create_table.sql

객체종류대상 · 시점동작
public.handle_new_user()함수 (plpgsql, SECURITY DEFINER)—profiles(id, username)에 (NEW.id, split_part(NEW.email, '@', 1)) INSERT
on_auth_user_created트리거auth.users · AFTER INSERT FOR EACH ROW위 함수 실행 → 가입 즉시 프로필 자동 생성
 
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
begin
    insert into public.profiles (id, username)
    values (new.id, split_part(new.email, '@', 1));
    return new;
end;
$$;

create trigger on_auth_user_created
    after insert on auth.users
    for each row execute function public.handle_new_user();
  • SECURITY DEFINER인 이유: 가입 시점에는 사용자 JWT가 없어 RLS 아래에서 profiles에 INSERT 할 수 없다. 함수 소유자 권한으로 실행해 정책을 우회한다. profiles에는 INSERT 정책이 없으므로 이 경로가 프로필을 만드는 유일한 방법이다.
  • 예: hong.gildong@company.com 가입 → username = 'hong.gildong'

6. 보안 · RLS (행 수준 보안)

코드 확인 세 테이블 모두 ENABLE ROW LEVEL SECURITY. 사용자 JWT로 접속하는 anon 클라이언트에는 아래 정책이 적용되고, 서버 전용 서비스 롤 클라이언트는 정책을 우회한다.

테이블정책명명령조건의미
profilesselect own profileSELECTauth.uid() = id내 프로필만 조회
update own profileUPDATEauth.uid() = id내 프로필만 수정 (현재 API 없음)
conversationsselect own conversationsSELECTauth.uid() = user_id내 대화만 조회 → 목록 · 소유 확인
insert own conversationsINSERTWITH CHECK auth.uid() = user_id다른 사람 명의로 대화 생성 불가
update own conversationsUPDATEauth.uid() = user_id내 대화만 수정
delete own conversationsDELETEauth.uid() = user_id내 대화만 삭제 → 남의 대화는 0건 삭제 = 404
messagesselect own messagesSELECTEXISTS (내가 소유한 conversations에 속함)내 대화의 메시지만 조회
insert own messagesINSERTWITH CHECK (내가 소유한 conversations에 속함)내 대화에만 메시지 추가
없는 정책도 설계다 — profiles INSERT/DELETE, messages UPDATE/DELETE 정책이 없다. 즉 사용자 토큰으로는 프로필을 만들거나 지울 수 없고(트리거 · 계정 삭제가 담당), 메시지를 고치거나 개별 삭제할 수 없다(대화 삭제 시 CASCADE만 허용). 채팅 기록의 불변성을 DB 수준에서 보장한다.

7. API ↔ 테이블 접근 매트릭스

코드 확인 백엔드는 두 종류의 Supabase 클라이언트를 쓴다. anon + 사용자 JWT(RLS 적용)와 service role(RLS 우회). 어느 경로로 어떤 테이블을 만지는지가 이 시스템의 실질적 접근 통제다.

8. Redis 데이터 구조

코드 확인 Redis는 원본이 아니라 사본·운영 기록이다. 캐시 실패는 예외로 올리지 않고 “캐시 없음”으로 처리한다(fail-open). 사용량 로그 저장소 연결 실패만 대시보드에서 503으로 드러난다.

키 패턴타입값수명 · 크기쓰는 곳읽는 곳
session:{sha256(access_token)}String (JSON){"id": "<uuid>", "email": "..."}TTL 300초토큰 검증 miss 시모든 🔒 요청
messages:{conversation_id}String (JSON 배열)MessageOut[] 직렬화 (최대 20건, 오름차순)TTL 300초 · 메시지 INSERT 시 DEL메시지 조회 miss 시메시지 조회 · 채팅 이력 구성
usage_log:{conversation_id}List (JSON 문자열){"requested_at","latency_ms","prompt_tokens","response_tokens","total_tokens"}LPUSH 후 LTRIM 0..49 → 최근 50건답변 스트림 정상 완료 시/analytics/*

usage_log 항목 예시

{
  "requested_at": "2026-09-09T01:31:20.512+00:00",
  "latency_ms": 6213,
  "prompt_tokens": 2527,
  "response_tokens": 183,
  "total_tokens": 2710
}
  • 토큰 원문을 키에 쓰지 않고 SHA-256 해시를 쓴다 — Redis가 유출되어도 토큰 재사용이 불가능하다.
  • 사용량 로그에는 질문·답변 본문, 이메일이 들어가지 않는다 (화면 설계서 7. 권한 및 데이터 기준과 일치).
  • 토큰 수가 null인 항목은 대시보드에서 “토큰 미수집”으로 집계된다. 형식이 깨진 항목은 건너뛰고 skipped_invalid_logs에 센다.

9. 인덱스 · 성능

후속 과제 SQL 파일에 명시적 인덱스 정의가 없다. 현재 확인된 인덱스는 PK(유니크) 뿐이다. 아래는 앱의 실제 쿼리 패턴에서 도출한 권장 인덱스이며 아직 적용되지 않았다.

쿼리 (API)조건 · 정렬권장 인덱스비고
내 대화 목록 (GET /me/conversations)WHERE user_id = ? ORDER BY created_at DESC(user_id, created_at DESC)RLS 조건과 정렬을 한 번에 커버
대화 소유 확인WHERE id = ? AND user_id = ?PK로 충분—
메시지 목록 · 채팅 이력WHERE conversation_id = ? ORDER BY created_at ASC LIMIT 20(conversation_id, created_at)FK 컬럼은 PostgreSQL이 자동 인덱스를 만들지 않으므로 필수에 가깝다. CASCADE 삭제 속도에도 영향
첫 사용자 메시지 판별 (제목 갱신)WHERE conversation_id = ? AND role = 'user' ORDER BY created_at, id LIMIT 1위 인덱스로 커버—
대시보드 대화 목록SELECT id, title ORDER BY id (500건씩 페이지)PK로 충분전체 스캔이지만 대화 수가 작음
 
-- 권장 (미적용)
create index if not exists idx_conversations_user_created
    on conversations (user_id, created_at desc);
create index if not exists idx_messages_conversation_created
    on messages (conversation_id, created_at);

용량 · 보존

  • messages.content는 TEXT이며 AI 답변은 보통 수백 자, 규정 요약 시 최대 수천 자. 대화당 메시지 수 제한은 없다.
  • 보존 기간 정책은 없다 (사용자가 대화를 삭제하기 전까지 영구). 운영 전환 시 비활성 대화 아카이빙 기준을 정할 필요가 있다.

10. 알려진 차이 · 후속 과제

#항목설계서구현 (코드 확인)권장 조치

부록. 참고 DDL

설계서 배포된 DDL 원문이 저장소에 없어 설계서 명세로부터 재구성한 것이다. 실제 Supabase 프로젝트의 정의와 다를 수 있으며, 트리거·RLS 부분은 SQL 파일 원문과 같다.

-- 사용자 프로필 (auth.users와 1:1, 트리거로 생성)
create table if not exists profiles (
    id          uuid primary key default gen_random_uuid(),
    username    varchar(30) not null,
    created_at  timestamptz not null default current_timestamp
);

-- 대화
create table if not exists conversations (
    id          uuid primary key default gen_random_uuid(),
    user_id     uuid not null references profiles(id) on delete cascade,
    title       varchar(100) default '새로운 대화',
    created_at  timestamptz not null default current_timestamp,
    updated_at  timestamptz not null default current_timestamp
);

-- 메시지
create table if not exists messages (
    id               uuid primary key default gen_random_uuid(),
    conversation_id  uuid not null references conversations(id) on delete cascade,
    role             varchar(20) not null,
    content          text not null,
    created_at       timestamptz not null default current_timestamp
);

-- 가입 시 프로필 자동 생성 (원문)
create or replace function public.handle_new_user()
returns trigger language plpgsql security definer set search_path = public as $$
begin
    insert into public.profiles (id, username)
    values (new.id, split_part(new.email, '@', 1));
    return new;
end; $$;
create trigger on_auth_user_created
    after insert on auth.users for each row execute function public.handle_new_user();

-- RLS (원문)
alter table profiles enable row level security;
alter table conversations enable row level security;
alter table messages enable row level security;

create policy "select own profile" on profiles for select using (auth.uid() = id);
create policy "update own profile" on profiles for update using (auth.uid() = id);
create policy "select own conversations" on conversations for select using (auth.uid() = user_id);
create policy "insert own conversations" on conversations for insert with check (auth.uid() = user_id);
create policy "update own conversations" on conversations for update using (auth.uid() = user_id);
create policy "delete own conversations" on conversations for delete using (auth.uid() = user_id);
create policy "select own messages" on messages for select using (
    exists (select 1 from conversations c where c.id = messages.conversation_id and c.user_id = auth.uid()));
create policy "insert own messages" on messages for insert with check (
    exists (select 1 from conversations c where c.id = messages.conversation_id and c.user_id = auth.uid()));
